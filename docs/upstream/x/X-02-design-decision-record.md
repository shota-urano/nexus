## 1. 記録の決まり

- 記録する判断の基準: 後から変えにくい、費用やリスクが大きい、依頼の文と違う方へ決めた、構造や主要な品質特性（`NFR`）に影響する、のどれかに当たる判断。
- 置き場所: この書類の中に1件1節で置く。2章の決定ログから各節にたどる。
- ID の付け方: `ADR-xxx` の3桁の連番。却下や置換になっても ID を再利用しない。
- 書き換えの禁止: 承認した記録の背景・決定・結果は書き換えない。判断を変えるときは新しい `ADR` を起こし、古い記録の状態を「置換」にする。
- 承認する人: 全ての判断を RD-01 SH01（本人）が承認する。
- AI が書いた記録: AI が書いた `ADR` は、RD-01 SH01 が全文を読むまで状態を「提案」にする。判断そのものを `Q` の答えで決めたときも同じ。

## 3. 記録

### ADR-001 英語の教材は構造化したデータで受け取り、NEXUS の表示部品で見せる

- 状態: 承認（2026-11-23。RD-01 SH01 が要約と全文の置き場所を示されて承認した）
- 背景: 依頼は、AI が毎回作る英語の教材の HTML を、隔離したオリジンの iframe で表示するとしている（依頼 2章、8章、10章 Phase 1）。構造化した JSON に移すかは「未決定」だった（依頼 2章）。sharpen は既に `read.json` から `read.html` を作っており、問題も `set.json` の構造化したデータで持っている（RD-01 1章）。本人は JSON への移行を今回の範囲に入れ（Q-010）、HTML を隔離して表示する仕組みは作らないと決めた（Q-016）。
- 評価の基準: 依頼 8章の安全の決まり（生成された HTML をアプリの DOM へそのまま埋め込まない）を守れるか。共通のチャットへ選んだ語句を渡しやすいか（依頼 2章）。作る量。
- 検討した案:

| 案 | 安全 | 選んだ語句をチャットへ渡す | 作る量 |
|---|---|---|---|
| A. HTML を隔離した iframe で表示する（依頼の Phase 1） | 隔離のオリジン、`sandbox`、CSP、`postMessage` の検証を設計する必要がある（依頼 8章） | iframe から親へ `postMessage` で送り、送り元と形を確かめる | 隔離の仕組みと、HTML ごとの選択の連携 |
| B. 構造化したデータを NEXUS の表示部品で見せる | 生成された HTML を表示しないので、HTML の隔離は要らない。データの検証は要る | 表示部品が語句と文の ID を持つので、そのまま渡せる | `read.json` と `set.json` の形に合わせた表示部品 |
| C. A と B の両方を作る | A と B の両方の手当てが要る | A と B の両方 | A と B を足した量 |

- 決定: B にする。sharpen の `read.json` と `set.json` を受け取り、NEXUS の表示部品で見せる。HTML を隔離して表示する仕組みは今回は作らない。
- 結果:
  - 良くなること: 隔離のオリジンと `postMessage` の設計が要らない。選んだ語句と文を ID 付きでチャットへ渡せる（依頼 6章の `selection`）。
  - 悪くなること: sharpen の `read.json` と `set.json` の形が変わると、NEXUS の表示部品も直す必要がある。今後 HTML で届く種類の情報が出てきたら、A の仕組みを改めて作る。
  - 新しく生まれる制約: 受け取る教材の形を NEXUS が決めて検証する（RD-10 で扱う）。
- 決定の確かさ: 新しい種類の情報を HTML で受け取る必要が出たら見直す。

### ADR-002 配信元の送り先の改修を NEXUS の範囲に入れる

- 状態: 承認（2026-11-23。RD-01 SH01 が要約と全文の置き場所を示されて承認した）
- 背景: 英語は sharpen、ニュースは brain-harness が、今は cerebellum に送っている（RD-01 1章）。本人は配信元を作ることは範囲外とした（Q-007）が、送り先を NEXUS に変える改修は範囲に入れ（Q-015、Q-019）、cerebellum への送信はやめる（Q-020）。ニュースには画像の URL とテーマを足して送り（Q-021）、英語の答えは NEXUS に残して sharpen が読む（Q-022）。
- 評価の基準: NEXUS に情報が届くまでを1つの範囲で確かめられるか。配信元の中身（選び方、教材の作り方、採点）に手を入れないか。
- 検討した案:

| 案 | 届くまでを確かめられるか | 配信元の中身に触るか |
|---|---|---|
| A. 送り先の改修も NEXUS の範囲に入れる | NEXUS の受け入れ基準で、届くところまで確かめられる | 送り先と送る項目だけ |
| B. NEXUS は受け取り口までにし、改修は本人が別に行う | NEXUS の側はサンプルでしか確かめられない | 触らない |

- 決定: A にする。sharpen と brain-harness の改修は、送り先、送る項目（ニュースの画像の URL とテーマ）、英語の答えを読む先に限り、NEXUS の書類（RD-10 など）で扱う。
- 結果:
  - 良くなること: 毎朝届く本物の情報で NEXUS を確かめられる。
  - 悪くなること: NEXUS の作業が、別の2つのリポジトリにまたがる。cerebellum の「今日」の画面で英語とニュースが「未着」になる（直すのは本人。Q-023）。
  - 新しく生まれる制約: sharpen と brain-harness の改修は、それぞれのリポジトリの決まり（AGENTS.md）に従う。
  - 切り替えの進め方: 切り替えるときは、配信元が3日間 cerebellum と NEXUS の両方に送り、3日が過ぎたら cerebellum への送信をやめる。やめた後に NEXUS に届かなかったときは、cerebellum に戻さずに直し、届かなかった日の分は配信元が送り直す（Q-062、Q-065 の答え。RD-15 4章）。
- 決定の確かさ: 配信元が増えたら、配信元ごとに範囲に入れるかを決める。

### ADR-005 AI は Claude Code の CLI（`claude -p`）を本人のサブスクリプションで動かす

- 状態: 承認（2026-11-23。RD-01 SH01 が要約と全文の置き場所を示されて承認した）
- 背景: AI を動かす仕組みは、`claude -p`、Messages API、Agent SDK が候補だった（依頼 3章、7章、11章）。本人は要件定義で決めると答えた（Q-063 の答え）。費用は今の Claude の契約の範囲で、従量の課金を足さない（Q-008 の答え）。公式の文書（code.claude.com の Agent SDK overview、Run Claude Code programmatically、Legal and compliance。2026-11-23 に読んだ）によると、Messages API は API キーで使った分だけ請求され、`claude -p` はサブスクリプションのログインで動かせる。ただしサブスクリプションのログインは「Claude Code の通常の利用」のためとされ、Agent SDK などで製品やサービスを作る開発者には API キーを求めている。
- 評価の基準: Q-008（従量の課金を足さない）、ストリーミング、ツールをウェブの検索とページの読み取りだけに限れるか（Q-029）、規約に合うか（Q-046）。
- 検討した案:

| 案 | 費用 | ストリーミングとツールの制限 | 規約 |
|---|---|---|---|
| A. `claude -p` を本人のサブスクリプションで | 契約の範囲（使える量はサブスクリプションの上限に従う） | `stream-json` と `--allowedTools`・`--permission-mode` で対応 | 自分で作ったサーバから呼ぶ使い方が「通常の利用」に入るかは、文書から言い切れない |
| B. Messages API を API キーで | 使った分だけ請求され、Q-008 に反する | ストリーミングと、ウェブの検索とページの取得のサーバ側のツールで対応 | アプリから呼ぶ正規の方法 |
| C. Agent SDK | 文書は API キーでの利用を案内しており、B と同じく従量になる | 対応 | B と同じ |

- 決定: A にする（Q-040 の答え。2026-11-23 本人）。Phase 3 の前に、本人がこの使い方を Anthropic に確かめる（RD-12 NFR-029、RD-15 AC36）。認められなければ B に替え、Q-008 を見直す。替えられるように、AI を呼ぶところは1か所にまとめる（依頼 7章の AIProvider）。
- 結果: 良くなること: 今の契約の範囲で動かせる。悪くなること: 本人の Claude Code のほかの利用と、サブスクリプションの使える量を分け合う。規約の確認が済むまで、Phase 3 の仕組みは確定しない。CLI は Mac mini の上で、改変せずに使う。
- 決定の確かさ: Phase 3 の前の確認の結果で見直す。

### ADR-007 DB は SQLite にする

- 状態: 承認（2026-11-24。RD-01 SH01 が全文を読んで「14まで問題なし」と承認した。判断は Q-068 で決めた）

| 案 | 動かすもの | バックアップ | 日本語の検索 | 量 |

- 評価の基準: NFR-016・NFR-019（AI を動かす環境をほかと分けられるか）、NFR-005（自動で戻るか）、`claude -p` のログインをそのまま使えるか、作る量。
- 検討した案:

| 案 | AI の環境を分けられるか | 自動で戻るか | `claude -p` のログイン | 作る量 |
|---|---|---|---|---|
| A. launchd で Web サーバと AI Runner の2つ | AI Runner だけ作業の場所と環境変数を絞れる | launchd が起動し直す | そのまま使える | 2つのプロセスの受け渡しが要る（ADR-012） |

| C. Docker Compose | コンテナで分けられる | Docker の再起動の設定 | コンテナの外で動かす工夫が別に要る | 多い |

- 決定: A にする（Q-069 の答え）。AI Runner は本人の macOS のユーザで動かす（Q-075 の答え）。
- 結果: 良くなること: AI を動かすところを1つのプロセスに閉じ込められ、Messages API に替えるときも AI Runner だけを替えればよい（ADR-005）。悪くなること: 2つのプロセスを launchd に載せ、受け渡しを作る。
- 決定の確かさ: Q-066 で Messages API に替えても、この形は変えない。

### ADR-010 端末の認証は、登録コードと端末の鍵にする

- 状態: 承認（2026-11-24。RD-01 SH01 が全文を読んで「14まで問題なし」と承認した。判断は Q-071 で決めた）
- 背景: NFR-013 は、本人が Mac mini の設定で用意した端末だけが使え、取り消した端末は次の利用から使えないとし、方式は基本設計で決めるとしている。依頼 0章は認証の方式を勝手に確定しないとしている。用意と取り消しは画面を持たない（Q-034 の答え）。
- 評価の基準: NFR-013 を満たすか、作る量、毎回の手間、端末をなくしたとき。
- 検討した案:

| 案 | 作る量 | 毎回の手間 | 端末をなくしたとき |

| A. 1回限りの登録コードを含む URL を端末で開き、端末に長く使える端末の鍵を置く（コードを入れる画面は作らない。Q-034） | 少ない | 無い | Mac mini のコマンドで鍵を消す |

- 決定の確かさ: 利用者が増えるか、NEXUS を Tailscale の外に出すときは見直す。

### ADR-012 Web サーバと AI Runner の受け渡しは、DB の待ち行列にする

- 状態: 承認（2026-11-24。RD-01 SH01 が全文を読んで「14まで問題なし」と承認した。判断は Q-073 で決めた）
- 背景: ADR-008 で Web サーバと AI Runner を別のプロセスにした。AI の実行は同時に2つまで、1回5分で打ち切り、取り消しが要る（NFR-017）。依頼 3章は「シンプルなDBキューまたはワーカー」を挙げている。
- 評価の基準: NFR-017 の上限を1か所で守れるか、再起動したときに仕事が残るか、質問と記事の関係の判定を同じ仕組みで扱えるか、応答の速さ（NFR-002）。

| 案 | 上限を守る場所 | 再起動 | 関係の判定 | 応答の速さ |

### ADR-013 AI の応答は SSE で端末へ流す

### ADR-014 ADR-002 の送る項目の範囲に、ニュースの元の記事の URL を足す

- 状態: 承認（2026-11-24。RD-01 SH01 が全文を読んで「14まで問題なし」と承認した。判断は Q-077 と CR-002 で決めた）
- 背景: ADR-002 は、配信元の改修を「送り先、送る項目（ニュースの画像の URL とテーマ）、英語の答えを読む先」に限った。基本設計で、brain-harness が元の記事の URL を別の項目で送っておらず、案内の本文の末尾のリンクにだけあると分かった（X-04 Q-077）。ADR-002 は承認済みなので書き換えず、範囲を広げた判断をここに残す。
- 評価の基準: ADR-002 と同じ（届くまでを確かめられるか、配信元の中身に手を入れないか）。
- 検討した案:

| 案 | 届くまでを確かめられるか | 配信元の中身に触るか |
|---|---|---|
| A. brain-harness が元の記事の URL を別の項目として送る | 項目の有無を NEXUS が確かめられる | 送る項目を1つ足すだけ。案内の書き方は変えない |

- 決定: A にする（Q-077 の答え。CR-002 で RD-10 と RD-16 を直した）。

- 決定の確かさ: ADR-002 と同じ。

### ADR-015 ニュースの図の部品は React Flow にする
